## 수백 TB 로그의 실시간 추적: Palantir audit.3의 스트리밍 전환

**분야:** 보안/거버넌스 | **중요도:** 8점

**Palantir 발행일:** 2025-12-04T14:59:39.168000Z

**수집일:** 2026-11-04

*수백 TB 규모 감사 로그의 실시간 가용성과 표준화 스키마를 통해 보안 거버넌스의 한계를 어떻게 돌파했는지 살펴본다.*

<mark>정부 기관이나 금융사가 Palantir 플랫폼에서 민감한 데이터를 다루는 동안, 누가 어떤 행위를 했는지 기록하는 감사 로그는 신뢰의 핵심이다.</mark> <mark>그러나 기존 시스템은 하루 수백 TB에 달하는 로그를 배치 처리로만 다루다 보니, 보안 사고 발생 시 즉각적인 대응이 불가능한 구조적 한계가 있었다.</mark>

Palantir는 이러한 문제를 해결하기 위해 'audit.3' 시스템을 정식 출시하며, 로그 수집부터 저장까지의 전 과정을 스트리밍 기반으로 재설계했다고 발표했다. 이번 발표는 단순한 성능 향상을 넘어, 보안 분석의 일관성과 실시간성을 확보하기 위한 아키텍처의 근본적 변화를 보여준다.

![Palantir 대표 이미지](https://miro.medium.com/v2/resize:fit:1200/1*T8SfUvBsTXaiYc1BwRLrkQ.png)

### 배치 처리의 한계와 스트리밍 파이프라인 도입

기존 audit.2 시스템은 로그를 배치 단위로 수집하고 여러 단계의 중간 데이터셋을 거쳐야 했기 때문에 지연 시간이 길고 아키텍처가 복잡했다. Palantir는 이 문제를 해결하기 위해 컨테이너 서비스와 함께 실행되는 분산 에이전트 기반의 '텔레메트리 수집 스트리밍 파이프라인'을 구축했다.

이 새로운 파이프라인은 로그 메타데이터를 기록 시점에 즉시 캡처하고, 중간 복사본 없이 객체 저장소(Blobstore)에 직접 기록한다. 이를 통해 로그 가용 시간이 수 분으로 단축되어, 보안 팀이 과거 분석용 자료가 아닌 실시간 운영 도구로 감사 로그를 활용할 수 있게 되었다.

### 이벤트 기반에서 카테고리 기반 스키마로의 전환

각각의 Palantir 제품이 독자적인 이벤트 구조를 정의했던 기존 방식은 분석가가 일관된 쿼리를 작성하기 어렵게 만들었다. audit.3는 모든 감사 가능 행위를 '데이터 내보내기(<strong>dataExport</strong>)', '인증 이벤트' 등 표준화된 카테고리로 매핑하는 철학적 전환을 시도했다.

개발 도구는 빌드 시점에 카테고리 요구사항을 강제하여, 새로운 기능이 추가되어도 기존 보안 규칙이 자동으로 적용되도록 한다. 예를 들어 새로운 데이터 내보내기 기능이 출시되면, 해당 카테고리를 모니터링하는 컴플라이언스 오피서의 로직은 수정 없이 새로운 기능을 커버하게 된다.

### 외부 SIEM 연동과 마이그레이션 전략

Palantir는 고객이 이미 구축한 보안 인프라를 대체하려 하지 않고, 새로운 공개 API를 통해 감사 로그를 직접 추출할 수 있게 했다. 보안 팀은 이 API를 통해 로그를 실시간으로 폴링하여 자신의 <strong>SIEM</strong>(Security Information and Event Management) 시스템에 직접 주입할 수 있다.

마이그레이션 과정에서는 audit.2와 audit.3가 동시에 실행되어 조직이 새로운 분석을 검증한 후 완전히 전환할 수 있도록 지원한다. 이는 대규모 시스템 변경 시 발생할 수 있는 리스크를 줄이고, 점진적인 채택을 가능하게 하는 실용적인 접근이다.

### 정리하면

audit.3의 정식 출시는 Palantir 플랫폼의 감사 로그가 실시간 보안 운영에 즉시 활용될 수 있음을 확인한 중요한 이정표다. 표준화된 스키마와 스트리밍 아키텍처는 향후 제품 확장에도 분석 일관성을 유지할 기반을 제공한다. 다만, 모든 고객이 <strong>SIEM</strong> 연동이나 마이그레이션을 완료하기까지는 시간이 소요되며, 실제 운영 환경에서의 최종 안정성은 점진적인 도입 과정을 통해 검증될 것이다.
