## 네트워크 끊겨도 앱이 대화하게: Palantir의 백엔드 없는 프론트엔드 통신 아키텍처

**분야:** 엔지니어링 | **중요도:** 8점

**Palantir 발행일:** 2026-04-02T16:18:22Z

**수집일:** 2026-10-29

*불안정한 네트워크 환경에서 Palantir 앱들이 어떻게 백엔드 없이 실시간으로 데이터를 주고받는지를 살펴본다.*

<mark>사용자가 지도 앱에서 특정 지역을 선택하면, 옆에 열린 대시보드 앱이 즉시 해당 지역의 데이터를 불러와야 한다.</mark> <mark>하지만 현장에서는 네트워크가 끊기거나 지연이 심해져 서버를 통한 통신이 불가능한 경우가 많다.</mark>

Palantir 프론트엔드 엔지니어링 팀은 이러한 문제를 해결하기 위해 '프론트엔드의 백엔드'라 불리는 앱 간 통신 프레임워크를 개발했다. 이 글은 Gaia와 Workshop을 예로 들어, 브라우저 API만으로 앱들이 어떻게 독립적으로 작동하면서도 서로 상태를 공유하고 명령을 실행하는지 그 메커니즘을 설명한다.

![Palantir 대표 이미지](https://miro.medium.com/1*s6-vWURWN2TAe4beczo-zA.png)

### 브라우저 API를 활용한 초기 프로토타입과 한계

Palantir 앱 간 상호작용은 초기 Java Swing 워크스페이스 시절부터 드래그 앤 드롭 형태로 존재해 왔다. 최근에는 사용자가 더 복잡한 상호작용을 요구하면서, Gaia와 Workshop을 연결하는 'Gaia Controller'라는 Workshop 위젯이 등장했다.

Gaia Controller는 브라우저의 <strong>BroadcastChannel</strong> API를 통해 다른 탭에서 보낸 메시지를 듣고 특정 지도를 찾아 연결을 수립한다. 이를 통해 Workshop의 버튼 클릭이 Gaia 지도의 상태를 변경할 수 있었지만, 모든 코드가 Workshop 안에 갇혀 있어 다른 앱으로 확장하는 데 한계가 있었다.

### 상태 공유와 명령 실행을 분리한 두 가지 프레임워크

팀은 Gaia Controller의 기능을 일반화하기 위해 '상태 공유'와 '일회성 명령 실행'이라는 두 가지 행동을 분리했다. '<strong>Shared State</strong>' 프레임워크는 앱이 데이터 모델과 이름을 정의하고, 미디어 타입(<strong>Media Type</strong>) 문자열을 기준으로 다른 앱과 상태를 자동으로 동기화하는 API를 제공한다.

'<strong>Commands</strong>' 프레임워크는 임의의 로직을 API로 노출하여 다른 앱이 호출할 수 있게 한다. 호출하는 앱은 명령 ID와 요청 객체를 제공하면 <strong>Commands</strong>가 이를 전달하고 응답을 반환한다. 이 구조를 통해 뉴욕시 건물을 Gaia에서 선택하면 Workshop에 동기화되고, Workshop에서 '원 그리기' 명령을 실행하면 Gaia에 주석이 생성되는 워크플로우가 가능해졌다.

### 정리하면

이 프레임워크는 현재 AIP 에이전트가 사용자의 로컬 앱을 제어하는 도구로 확장되어, 단일 프롬프트로 지도 탐색 및 주석 달기 등 복합 작업을 수행하는 데 활용되고 있다. 모든 처리가 클라이언트 사이드에서 이루어지므로 네트워크 불안정 환경에서의 신뢰성은 확보되었으나, 이는 Palantir 내부 앱 생태계와 AIP 에이전트 통합에 초점을 맞춘 구현 방식이다.
