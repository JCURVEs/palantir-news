## 신호 없는 현장에서 엔터프라이즈 앱이 살아남는 법: 임베디드 온톨로지

**분야:** 엔지니어링 | **중요도:** 8점

**Palantir 발행일:** 2026-03-31T16:39:52Z

**수집일:** 2026-10-29

*네트워크 의존도를 제거하고 기기를 데이터 노드로 전환하는 Palantir의 임베디드 온톨로지 아키텍처를 살펴본다.*

<mark>현장 서비스 기술자가 신호가 없는 기계실에서 장비를 점검할 때, 기존 모바일 앱은 로딩 스피너가 멈추지 않거나 기능이 아예 작동하지 않는 경우가 많다.</mark> <mark>이는 모든 사용자 행동이 네트워크 요청으로 변환되기 때문에, 연결이 끊기면 앱이 단순한 껍데기로 전락하기 때문이다.</mark>

Palantir는 이러한 한계를 극복하기 위해 모바일 기기를 원격 플랫폼을 들여다보는 얇은 클라이언트가 아닌, 분산 데이터 시스템의 노드로 재정의하는 임베디드 온톨로지(Embedded Ontology)를 발표했다. 이 글은 해당 아키텍처가 어떻게 오프라인 환경에서도 완전한 기능을 유지하는지, 그리고 개발자가 이를 어떻게 구현하는지 구체적으로 살펴본다.

![Palantir 대표 이미지](https://miro.medium.com/1*alZ1qX36TB8EAMkxkXxRHA.png)

### 로컬 데이터와 글로벌 컨텍스트의 분리

임베디드 온톨로지는 데이터를 로컬 객체와 글로벌 컨텍스트 객체 두 층으로 나눈다. 로컬 객체는 기기의 작업 집합으로, 연결 상태와 무관하게 밀리초 지연으로 생성, 업데이트, 조회된다.

반면 글로벌 컨텍스트 객체는 조직의 배경 정보로, 자산 등록부나 작업 지시서처럼 자주 변하지 않지만 로컬 액션에 의미를 부여하는 데 필수적이다. 기술자가 점검 결과를 기록할 때는 로컬 스토어에 즉시 쓰여지며, 네트워크 왕복이나 지연이 발생하지 않는다.

### 오프라인을 '저하 모드'가 아닌 '기본 상태'로

동기화 모델은 최초 연결 시 필요한 객체 집합을 부트스트랩하고, 연결 중에는 양방향으로 변경 사항을 동기화한다. 연결이 끊겨도 기기는 정상적으로 작동하며, 읽기 작업은 로컬 스토어를 조회하고 쓰기 작업은 로컬에 인텐트(intent)로 캡처된다.

재연결 시 큐에 쌓인 쓰기 작업이 상류로 조정되고 충돌 해결이 자동으로 수행된다. 이때 앱은 '오프라인 상태'라는 배너를 표시하지 않으며, 사용자는 연결 여부를 인지하지 못한 채 동일한 사용자 경험을 유지한다.

### 캐싱이 아닌 분산 데이터 아키텍처

임베디드 온톨로지는 단순한 성능 최적화 수단인 캐시와 구별된다. 기기는 자체적인 로컬 스토어, 쿼리 엔진, 액션 실행 계층을 갖추고 있어 분산 데이터 시스템의 일부로 기능한다.

개발자는 Developer Console에서 필요한 객체 타입만 선택하여 TypeScript SDK를 생성하고, Vite 플러그인을 통해 WebAssembly 지원을 설정한다. 이 과정을 통해 기기에는 해당 역할에 필요한 최소한의 온톨로지 투영만 물질화된다.

### 연결성을 인지하지 않는 코드 구조

구현 단계에서 개발자는 네트워크 체크나 오프라인 폴백 로직을 작성할 필요가 없다. 애플리케이션 코드는 로컬 온톨로리를 쿼리하고 로컬 액션을 실행하는 데만 집중한다.

예를 들어 점검 이벤트를 기록하는 함수는 자산 태그를 로컬에서 조회하고 작업 지시서를 확인한 후 액션을 적용한다. 동기화 계층이 나머지 네트워크 처리를 담당하므로, 앱은 온라인이든 오프라인이든 동일한 코드 경로로 실행된다.

### 정리하면

임베디드 온톨로지는 엔터프라이즈 애플리케이션이 신호가 없는 현장에서도 신뢰할 수 있는 도구로 기능할 수 있는 기반을 제공한다. 다만 적응형 동기화 정책이나 온디바이스 AI 모델 결합 등 향후 발전 방향은 아직 초기 단계이며, 실제 운영 환경에서의 확장성은 추가적인 검증이 필요하다.
