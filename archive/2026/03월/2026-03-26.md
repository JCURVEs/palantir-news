## 6,000개 저장소의 연동 문제, GitHub 봇 조합으로 해결하다

**분야:** 엔지니어링 | **중요도:** 8점

**Palantir 발행일:** 2026-03-26T15:04:29.968000Z

**수집일:** 2026-10-29

*GitHub 웹훅과 무상태 봇을 조합해 수천 개 저장소의 반복적 운영 업무를 자동화하는 Palantir의 엔지니어링 접근법을 살펴본다.*

<mark>수천 개의 저장소가 독립적으로 운영되는 환경에서 하나의 라이브러리 버전을 업데이트하거나 CI 설정을 변경하려면 개발자가 각 저장소를 일일이 찾아다니며 수동으로 작업을 수행해야 한다.</mark> <mark>이 과정에서 발생하는 컨텍스트 스위칭과 반복적 노작(toil)은 개발 생산성을 크게 저해하는 주요 원인이 된다.</mark>

Palantir는 이러한 횡단적 문제를 해결하기 위해 단일 플랫폼 재작성 대신, GitHub의 네이티브 기능을 활용하는 독립적인 봇들을 점진적으로 구축했다. 이 글은 이러한 도구들이 어떻게 조합되어 인간 개입 없는 자동화 워크플로우를 형성하는지, 그리고 대규모 운영에서 마주친 실패 모드를 어떻게 관리하는지 구체적으로 살펴본다.

### GitHub 네이티브 원시를 활용한 독립적 봇 설계

Palantir의 솔루션은 단일 플랫폼이 아니라, GitHub의 웹훅, 상태, 체크, 라벨, 풀 리퀘스트라는 네이티브 원시를 통해 연결되는 독립적인 애플리케이션들의 집합이다. 각 봇은 유닉스 철학처럼 '한 가지 일을 잘하는' 방식으로 설계되어, GitHub가 워크플로우를 연결하는 조직액(Connective Tissue) 역할을 수행한다.

이러한 설계는 표준화된 빌드 태스크와 릴리스 프로세스를 모든 저장소에 적용함으로써 전체적인 마찰을 줄이는 효과를 낸다. 봇들은 서로의 상태를 직접 관리하지 않고, GitHub의 이벤트 시스템에 반응함으로써 워크플로우가 자연스럽게 구성된다.

### 대규모 저장소 운영을 위한 핵심 봇들의 역할

Policy-Bot은 GitHub의 기본 분기 보호 규칙이 제공하지 못하는 복잡한 조건부 승인 정책을 지원하며, 경로, 작성자, 팀 기반의 명세적 규칙을 적용한다. Bulldozer는 모든 필수 상태 체크가 통과하고 병합 준비 라벨이 존재할 때 자동으로 PR을 병합하는 무상태(<strong>stateless</strong>) 봇으로, 중복 웹훅 처리에도 안전하다.

Excavator는 샌드박스 컨텍스트에서 프로그램을 실행해 대량의 저장소에 의존성 업데이트나 리팩토링을 적용하고 PR을 생성하는 분산 시스템이다. Label Maker는 변경된 파일 경로나 작성자 등 조건에 따라 라벨을 자동으로 부여하여 다른 봇들의 트리거 역할을 하며, Nit은 CI 실패 중 기계적으로 수정 가능한 포맷이나 락파일 오류를 직접 수정 커밋으로 해결한다.

### 의존성 업데이트부터 배포까지의 자동화 흐름

CVE 해결을 위한 라이브러리 업그레이드 사례를 보면, Excavator가 새 버전을 감지해 각 저장소에 PR을 열고 락파일을 재생성한다. Label Maker는 이 PR에 병합 준비, 자동 릴리스, 오류 수정 라벨을 붙이고, CI 실행 중 기계적 오류가 발생하면 Nit이 자동으로 수정 커밋을 푸시하여 CI를 재실행시킨다.

Policy-Bot은 봇이 생성한 PR의 경우 파일 범위와 서명 키를 검증하여 승인 상태를 성공으로 설정하고, Bulldozer가 이를 병합한다. 이후 Autorelease가 버전화된 릴리스를 생성하고 Apollo를 통해 배포를 조정하는 과정에서, 워크플로우가 설정된 후에는 인간 개입 없이 의존성 업데이트, 테스트, 컴플라이언스 체크, 배포가 완료된다.

### 대규모 실패 모드를 관리하는 속도 제한

자동화는 완벽하지 않으며, 대규모 실행 시 예상치 못한 부하를 유발할 수 있다. 과거 백포트 봇이 모노레포의 모든 버전에서 동시에 실행되어 CI 포화와 아티팩트 호스팅 과부하를 일으켜 다른 개발자의 테스트를 방해한 사례가 있었다.

이러한 문제를 방지하기 위해 Backport와 Excavator에는 단일 호출 시 생성할 수 있는 PR 수에 대한 상한선(upper bounds)이 적용된다. 이는 GitHub 웹훅 인프라에 가해지는 부하를 제한하고, 대규모 자동화 작업이 시스템 전체의 안정성을 해치지 않도록 하는 중요한 안전장치로 기능한다.

### 정리하면

Palantir의 접근법은 단일 플랫폼 구축이 아니라, 특정 공백을 메우는 독립적 도구들의 점진적 조합을 통해 개발자의 운영적 부담을 줄이는 데 초점을 맞춘다. 무상태 설계와 명세적 설정을 통해 확장성을 확보했지만, 대규모 실행 시 발생할 수 있는 CI 포화 등 실패 모드를 관리하기 위한 속도 제한 등 지속적인 모니터링과 제약 조건 설정이 필수적이다.
